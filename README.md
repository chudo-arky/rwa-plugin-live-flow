# rwa-plugin-live-flow

[![CI](https://github.com/chudo-arky/rwa-plugin-live-flow/actions/workflows/ci.yml/badge.svg)](https://github.com/chudo-arky/rwa-plugin-live-flow/actions/workflows/ci.yml)

![Python](https://img.shields.io/badge/Python-3.11%2B-blue)

Живая схема трафика для [remnawave-admin](https://github.com/Case211/remnawave-admin):
пользователи → ноды → выходы, с реальным онлайном и VPN-скоростью из панели Remnawave.

![Live Flow — схема трафика](docs/live-flow.svg)

> **English:** A read-only remnawave-admin plugin that visualizes live traffic
> from users through nodes to configured exits. It shows active users, VPN
> throughput and connection details, with separate permissions for the diagram
> and personal data. No external telemetry.
>
> Requires remnawave-admin Plugin API v1, Python 3.11+ and a single backend worker.
> Installation: download the wheel from [Releases](https://github.com/chudo-arky/rwa-plugin-live-flow/releases/latest)
> and upload it through **Administration → Plugins**.

> [!NOTE]
> Плагин работает только на чтение: не изменяет базу remnawave-admin,
> конфигурацию панели или пользователей и не использует внешнюю телеметрию.

## Возможности

- Живая схема «пользователи → ноды → выходы» с обновлением каждые 5 секунд, подгонкой под окно и масштабированием (кнопки, колесо мыши, перетаскивание).
- Для больших парков: страницы (в «столбце» — по 50 нод при парке больше 50, в режиме «колонки» — по 20), поиск и фильтры «только активные» / «только с трафиком».
- Реальный онлайн и VPN-скорость по счётчикам xray панели (а не по сетевой карте хоста).
- Группировка пользователей по типу сети: мобильная, Wi-Fi/LAN, через CDN (входы, помеченные в конфиг-профиле, см. [«Метка CDN в конфиге»](#метка-cdn-в-конфиге); без меток — угадывается по настройкам инбаунда), неизвестная — толщина линии показывает
  число активных пользователей этой группы на ноде, бегущий пунктир — идёт трафик.
- Линии к веткам выходов, по которым реально идёт трафик ноды (WARP, цепочки, каскады), по счётчикам панели; расклад в процентах — в подсказке ноды.
- Кто ушёл в каскад и в конкретный выход — по фактическому аутбаунду из access.log (нужен агент, присылающий `outbound_tags`).
- Подсказки о проблемах сбора: агент ноды молчит; у инбаунда за прокси не задан `trustedXForwardedFor`, и Xray видит всех как `127.0.0.1`.
- Автоматическое отображение выходов DIRECT, BLOCK, WARP, цепочек и каскадов между нодами — по конфиг-профилям панели. Аутбаунды, вынесенные в сниппеты панели (`{"snippet": "имя"}`), раскрываются. Каскад (аутбаунд на другую свою ноду) рисуется дугой нода → нода; цель узнаётся по адресу или по IP после DNS-резолва обеих сторон.
- Списки подключённых пользователей по клику на ноду или группу: логин, IP (в т. ч. IPv6), ASN, геолокация, инбаунд, нода. Где агент не читает access.log, IP берётся из карты онлайн-IP панели (помечен `◦`); устаревшие строки подключений отсекаются.
- Ноды в том же порядке, что и в панели; интерфейс на русском и английском — следует за языком админки.
- Раздельные права на схему и на персональные данные.
- Только чтение, без внешней телеметрии и изменений в базе.

## Установка

### Через интерфейс админки — рекомендуется

1. Скачайте файл `.whl` из [последнего релиза](https://github.com/chudo-arky/rwa-plugin-live-flow/releases/latest)
   (пре-релизы с новыми возможностями — на странице [Releases](https://github.com/chudo-arky/rwa-plugin-live-flow/releases)).
2. Откройте **Администрирование → Плагины → Загрузить wheel**.
3. Выберите скачанный файл и перезапустите backend remnawave-admin.

При обновлении загрузите новый wheel тем же способом — админка удалит предыдущую
версию автоматически. Удаление — убрать wheel из каталога `plugins/` и перезапустить
backend: таблиц и миграций у плагина нет, после удаления в базе ничего не остаётся.

### Ручная установка

```bash
cp rwa_plugin_live_flow-*.whl /opt/remnawave-admin/plugins/
docker restart remnawave-web-backend
```

Перед ручным обновлением удалите старый wheel из каталога `plugins/`, иначе backend
может попытаться установить обе версии.

### Сборка из исходников

```bash
git clone https://github.com/chudo-arky/rwa-plugin-live-flow.git
cd rwa-plugin-live-flow
python -m pip install build
python -m build
```

Готовый wheel появится в каталоге `dist/`.

## Совместимость

| Компонент | Требование |
|---|---|
| remnawave-admin | Plugin API **v1**; страница внутри админки — с **4.5.4** (generic-маршрут `/plugins/:pluginId`); на более старых — пункт меню + standalone-страница `/api/v2/plugins/live_flow/ui`. Проверено на **4.8.2**. Методы клиента панели, которых нет в старой админке, плагин проверяет при запуске и без них просто не показывает соответствующие данные |
| Панель Remnawave | 3.x (проверено на 3.4.3), всё под API-токеном админки — см. таблицу ниже |
| Python | 3.11+ |
| Backend-воркеры | один (см. «Ограничения») |

Запросы к панели:

| Запрос | Для чего | Если недоступен |
|---|---|---|
| `GET /api/nodes`, `GET /api/users` | онлайн, активные, скорость VPN | схема берёт данные синка админки (лаг до 5 мин) |
| `GET /api/config-profiles`, `GET /api/config-profiles/{uuid}/computed-config` | выходы, каскады, сниппеты, метки CDN | последний удачный набор с пометкой «устарела» |
| `GET /api/system/nodes/metrics` | линии к веткам выходов с трафиком | ветки без измерений, линии только в интернет |
| `POST` и `GET /api/connections/by-node/…` | IP там, где агент ноды не читает access.log | IP только от агента |

Если API-токен админки ограничен по правам, ему нужны эти операции. Токенам с ролью ADMIN проверка прав не требуется.

> [!IMPORTANT]
> Сейчас поддерживается один backend worker. При нескольких workers каждый
> процесс будет отдельно опрашивать панель, увеличивая нагрузку.

## Права и персональные данные

Плагин регистрирует ресурс `live_flow` с двумя действиями:

| Право | Что открывает |
|---|---|
| `live_flow:view` | схема, агрегаты, скорости, счётчики (`/data`, `/ui`, `/app`, `/ui-module`) |
| `live_flow:view_users` | списки людей: логин/email, Telegram ID, тег, IP, AS, страна/город, нода, инбаунд (`/node/{uuid}/users`, `/group/{group}/users`, `/cascade/{uuid}/users`, `/exit/users?tag=…`) |

Маршруты списков:

| Маршрут | Что отдаёт |
|---|---|
| `GET /node/{uuid}/users` | кто сейчас на ноде |
| `GET /group/{group}/users` | сводный список по типу сети: `mobile` · `fixed` · `cdn` · `unknown` · `all` |
| `GET /cascade/{uuid}/users` | кто на нодах, каскадящих на ноду `uuid` (`kind: cascade`, `target`, `nodes`) |
| `GET /exit/users?tag=…` | кто на нодах, у которых есть выход с тегом `tag` (`kind: exit`, `sink`, `nodes`). Тег передаётся query-параметром: теги xray могут содержать `/`, кавычки и Unicode; прежний `GET /exit/{tag}/users` оставлен для тегов без `/` |

Списки по каскаду и выходу строятся **по факту** (`by_outbound: true`), если агент ноды
присылает выбранные аутбаунды (`outbound_tags`): остаются только те, у кого эта ветка
действительно встретилась в access.log. Иначе — по нодам (`by_nodes: true`): все активные на
нодах, где такая ветка есть, с оговоркой, что выбранный аутбаунд не виден.

Суперадмин получает оба права при регистрации плагина; остальным ролям `view_users`
выдавайте осознанно — без него интерфейс не предлагает клики по нодам и группам, а API
отвечает 403. Все JSON-ответы отдаются с `Cache-Control: private, no-store`.

## Откуда данные

| Что на схеме | Источник | Как часто |
|---|---|---|
| счётчик онлайна ноды | `usersOnline` панели (считает и пинги клиентов с авто-выбором серверов) | опрос панели каждые 15 с |
| реально активных | `userTraffic.onlineAt` + `lastConnectedNodeUuid` юзеров панели, окно 180 с от текущего времени | опрос панели каждые 15 с |
| скорость VPN ноды / юзера | дельты счётчиков xray панели `trafficUsedBytes` / `usedTrafficBytes` между двумя последними разными значениями | панель двигает их каждые ~30 с / ~15 с |
| тип сети юзера (мобильный / Wi-Fi-LAN) | `ip_metadata` админки по последнему IP юзера (`is_mobile`, `connection_type`) | кеш 45 с |
| IP / AS / гео в списках | `user_connections` (агент rw-admin) + `ip_metadata` админки; строка, чей адрес снимок панели уже не видит и которая старше снимка, отбрасывается | на открытие списка |
| форма выходов, каскады | конфиг-профили панели; профили со ссылками на сниппеты — через `computed-config` панели (раскрытый конфиг), у старой админки без этого метода — по списку сниппетов | кеш 60 с (при ошибке профилей или сниппетов — последний удачный набор с пометкой `profiles_stale`; на холодном старте без панели — `profiles_available: false`) |
| сетевая скорость хоста (в тултипе) | `net_tx_bps` / `net_rx_bps` агента rw-admin — **весь** NIC хоста, справочно | агент, 30 с |
| доля трафика по веткам выходов | `GET /api/system/nodes/metrics` панели — счётчики xray по каждому inbound- и outbound-тегу ноды | опрос каждые 30 с, доля считается по окну 10 мин |
| состояние агента ноды (в тултипе) | `nodes.metrics_updated_at` + свежие строки `user_connections` по этой ноде | кеш 60 с |
| IP там, где агент не читает лог | `POST/GET /api/connections/by-node` панели — карта онлайн-IP xray | обход нод по кругу, снимок не старше 90 с |

Если опрос панели недоступен, схема переключается на данные синка админки (лаг до 5 мин),
в шапке видно «синк БД»; при ошибке опроса показывается только её код.

**Каскад.** Аутбаунд-цепочка на другую свою ноду (совпадение по адресу или по IP после
DNS-резолва обеих сторон) — не выход, а прыжок: в колонке «Каскад» стоит карточка «через
ноду-цель», в неё идёт линия из ноды-источника, из неё — к выходам ноды-цели. Сама нода-цель
остаётся в общем столбце со своими пользователями и выходами. Клик по карточке-прыжку
показывает активных на нодах-источниках.

**Сниппеты и недоступность конфигурации.** Профили со ссылками на сниппеты плагин берёт у
панели уже раскрытыми (`GET /api/config-profiles/{uuid}/computed-config`, один запрос на такой
профиль; обычные профили — без лишнего запроса). Если панель не ответила на запрос профилей или сниппетов,
схема держит последний удачный набор с пометкой «конфигурация выходов устарела» в легенде;
если удачного набора ещё не было — «конфигурация выходов недоступна», выходы не рисуются.
Ссылка на несуществующий сниппет не подменяется выходом DIRECT: у такой ноды выходов нет, а в
легенде видно «сниппеты не раскрыты: имя». DIRECT по умолчанию подставляется только когда у
ноды нет профиля или в его конфиге не было выходов вовсе.

**Ветки выходов.** Панель считает байты по каждому тегу аутбаунда. По ним плагин тянет линии
к веткам, куда за последние 10 минут реально шёл трафик ноды, — к WARP, цепочкам, каскадам, а
не только в интернет. Расклад в процентах — в подсказке карточки ноды. Оговорки:

- **это доли, а не Мбит/с.** Панель отдаёт не байты, а строки вида `"12.34 GiB"` с шагом
  0.01 единицы (на GiB это 10.7 МБ, на TiB — 11 ГБ); абсолютную скорость по ним не восстановить.
- **тихая нода остаётся «без измерений»**: пока дельта за окно меньше двух шагов строки, ни линий,
  ни долей нет. Счётчик кумулятивный, и на большом аптайме панели таких нод станет больше — это
  граница метода, а не сбой.
- Ветка, по которой за окно ничего не прошло, линии не получает.

**Кто ушёл в каскад или в конкретный выход.** Если агент ноды присылает `outbound_tags`
(вторая половина скобок `[инбаунд -> аутбаунд]` из access.log), списки по клику на прыжок каскада
и на выход сужаются до тех, у кого эта ветка действительно встретилась. Это «за последние минуты
человек ходил через неё», а не «весь его трафик идёт туда»: за один батч один пользователь уходит
в несколько веток сразу, а байтов по веткам access.log не содержит. Со старым агентом, который
поля не шлёт, остаётся прежний список — все активные на нодах-источниках.

**Чего плагин не знает:** доли трафика **по конкретному пользователю** между его ветками.
Каскад на уровне ядра (WireGuard в обход xray) не виден вовсе.

**Состояние агента ноды.** В подсказке карточки видно, почему по ноде нет IP: *агент молчит*
(метрик нет больше 5 минут) или *агент жив, но access.log не читается* — второе ставится, только
когда на ноде есть онлайн, а агент не прислал по ней ни одной строки. Признак намеренно слабый:
открытые строки подключений админка закрывает только из батча агента, поэтому у ноды с
выключенным логом прежние строки висят и её не выдают. Сверять их с картиной панели нельзя —
привязку строки к ноде переписывает любой отчитавшийся агент.

## Ограничения

- **Один backend-worker.** Опрос панели живёт в памяти процесса; при нескольких uvicorn-воркерах
  каждый опрашивает панель сам (нагрузка ×N, данные у каждого корректные). Плагин пишет
  предупреждение в лог, если видит `WEB_CONCURRENCY`/`UVICORN_WORKERS` > 1.
- Опрос обрезается на 20 000 пользователях (срез помечается `truncated`).
- Направления ↑/↓ у VPN-скорости нет — панель отдаёт один счётчик.
- **«Сеть неизвестна» у всех или почти всех.** Тип сети берётся из `user_connections` → `ip_metadata`
  админки, поэтому «неизвестно» — это не сбой плагина, а отсутствие данных. Наведите курсор на карточку
  «Сеть неизвестна» — во всплывающей подсказке видно причину и сколько пользователей за ней:
  - *агент ноды не сообщил IP* — на ноде не работает агент remnawave-admin или он не видит access-лог Xray.
    Плагин пробует добрать такой IP у панели (`by-node`, карта онлайн-IP самого Xray) — в списках он помечен `◦`.
    Тега инбаунда у такой записи нет: его знает только access.log, поэтому группа «Предположительно CDN» по ней не считается;
  - *IP ещё без GeoIP* — обогащение отстаёт (без MaxMind `ip-api.com` даёт ~45 запросов/мин);
  - *за CDN/прокси* — Xray видит адрес CDN, хостинга или локального прокси (127.0.0.1), а не клиента. Какой вход
    считается CDN, решает [метка в конфиге](#метка-cdn-в-конфиге); без меток — эвристика по настройкам инбаунда
    (HTTP-транспорт без Reality, `security: none` или задан `trustedXForwardedFor`), и тогда группа подписана
    «Предположительно CDN»: обычный nginx с такими же настройками получит ту же метку. Как увидеть адрес клиента,
    не открыв подмену, — раздел [«Адрес клиента за CDN и обратным прокси»](#адрес-клиента-за-cdn-и-обратным-прокси).

История изменений — [CHANGELOG.md](CHANGELOG.md).

## Адрес клиента за CDN и обратным прокси

Всё ниже проверено на стенде с Xray 26.7.28 и nginx 1.31 (13.09.2026). Плагин тут ничего не настраивает — это конфигурация origin и инбаунда; плагин только показывает результат и подсказывает, когда адреса не видны.

### Почему у всех 127.0.0.1

Инбаунд с HTTP-транспортом (xhttp, ws, httpupgrade, grpc) на `127.0.0.1` стоит за обратным прокси. Без `sockopt.trustedXForwardedFor` Xray берёт адрес самого прокси и пишет каждого пользователя как `127.0.0.1` — так настраивают CDN большинство популярных руководств. Слепнет всё, что опирается на IP: гео, ASN, деление по типу сети. Xray не кладёт loopback и в карту онлайн-IP, так что снимок панели адреса тоже не даст. Такие инбаунды плагин показывает в подсказке ноды.

### Почему нельзя просто включить trustedXForwardedFor

Если nginx дописывает заголовок (`proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for`, тоже частый рецепт), Xray берёт **первый** адрес из цепочки — тот, что прислал сам клиент. Аутентифицированный пользователь, подключившийся к origin напрямую, запишет себе в учёт любой адрес. Проверено: клиент прислал `203.0.113.99` — ровно он и попал в access.log.

Для этой версии ядра `trustedXForwardedFor` работает со **списком имён заголовков**. Форма со списком адресов (`["127.0.0.1/32"]`) для прокси на loopback не сработала: ядро отбрасывает заголовок как «потенциально поддельный».

### Рабочая схема: доверять заголовку только от CDN

Инбаунд:

```json
"sockopt": { "trustedXForwardedFor": ["X-Forwarded-For"] }
```

nginx на origin — один из двух вариантов.

**Вариант 1. По адресам CDN.** Нужен актуальный список опубликованных префиксов именно CDN, а не всех адресов облака провайдера.

```nginx
set_real_ip_from 192.0.2.0/24;          # каждый префикс CDN отдельной строкой
real_ip_header   X-Forwarded-For;
real_ip_recursive on;                    # обязательно: иначе при двух узлах CDN запишется адрес узла

location /ваш/туннельный/путь {
    proxy_pass http://127.0.0.1:ПОРТ;
    proxy_set_header X-Forwarded-For $remote_addr;   # перезапись, не дописывание
    # … остальное как было
}
```

Пропущенный префикс — подключения с него запишутся адресом узла CDN; лишний — подменить адрес сможет любой, кто арендует машину в этом диапазоне.

**Вариант 2. По секретному заголовку, без списка адресов.** CDN добавляет к запросам в origin непубличный заголовок (Yandex Cloud CDN: «HTTP-заголовки и методы» → «Заголовки запросов к источнику»; Timeweb Cloud: «Управление» → «HTTP-заголовки» → «Заголовки запросов»), nginx проверяет его значение.

```nginx
map $http_x_origin_secret $from_cdn { default 0; "длинная-случайная-строка" 1; }
map $http_x_forwarded_for $xff_last { default ""; "~(?<last>[^,[:space:]]+)[[:space:]]*$" $last; }
map $from_cdn $client_ip { 1 $xff_last; default $remote_addr; }

location /ваш/туннельный/путь {
    proxy_pass http://127.0.0.1:ПОРТ;
    proxy_set_header X-Forwarded-For $client_ip;
    proxy_set_header X-Origin-Secret "";             # дальше origin секрет не уходит
    # … остальное как было
}
```

Схема берёт **последний** адрес из `X-Forwarded-For` — тот, что дописал сам CDN. Перед включением убедитесь, что ваш CDN дописывает туда адрес клиента, а не адрес своего промежуточного узла: один раз запишите `$http_x_forwarded_for` в лог origin. Секрет надёжен, пока знают его только CDN и origin.

### Метка CDN в конфиге

Сам плагин отличить вход через CDN от прямого подключения не может: для origin узел CDN и клиент — одинаковые TLS-клиенты, а отличить их можно только доверяя CDN (его секрету или адресам). Поэтому решает владелец: пометьте вход прямо в конфиг-профиле панели полем `liveFlow`:

```json
{
  "tag": "Moscow CDN",
  "listen": "127.0.0.1",
  "port": 4444,
  "protocol": "vless",
  "liveFlow": { "cdn": true },
  "streamSettings": { … }
}
```

- **Хоть одна метка на установке** — группа называется «Через CDN» и считается **только** по помеченным входам; угадывание выключается везде.
- **Меток нет** — всё как раньше: группа «Предположительно CDN», вход угадывается по настройкам (HTTP-транспорт без Reality, `security: none` или задан `trustedXForwardedFor`).
- Значение — именно `true`: строка `"true"` меткой не считается.

Поле безопасно для ядра и панели — проверено 13.09.2026: Xray 26.7.28 принимает неизвестные поля (`xray run -test` — Configuration OK), панель сохраняет конфиг как есть. Добавление метки панель считает правкой инбаунда, привязки хостов, сквадов и нод сохраняются. Сохранение профиля панель рассылает на ноды, так что делайте это как любую правку конфига.

⚠️ **Не переименовывайте ради метки сам тег инбаунда.** Панель узнаёт инбаунды по тегу: новое имя для неё — удаление старого входа и создание нового. Хосты теряют привязку, из внутренних сквадов и с нод вход удаляется.

Метка — утверждение владельца, а не доказательство. Если прямое подключение к origin возможно, оно попадёт в помеченный вход и тоже будет посчитано «через CDN».
